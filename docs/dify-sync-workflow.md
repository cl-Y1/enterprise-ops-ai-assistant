# Dify 知识库更新衔接流程

> 适用于企业智能运维知识助手 V1.4 文档版本管理模块。<br>
> 目标：让“本地文档变更”与“Dify 知识库生效”之间有清晰、可追溯、可回滚的交接，而不是直接覆盖生产知识库。

## 1. 设计原则

1. **本地先留痕，再更新 Dify**：每个版本先有更新原因、更新人、内容快照和提交人。
2. **审核、同步、发布分离**：审核通过只代表内容可进入 Dify 同步阶段。
3. **提交人不能自审**：审核人与提交人必须是不同账号。
4. **Dify 更新需要人工确认**：替换知识库文档会触发重新分段和索引。
5. **发布前必须验证**：Dify 同步、索引成功、RAG 验证通过，管理员才能发布。
6. **历史不可丢失**：新版本发布后，旧发布版本自动归档，内容仍可下载。
7. **默认不自动写入知识库**：V1.4 使用人工交接，避免误覆盖生产知识库。

## 2. 角色与职责

| 角色 | 职责 |
| --- | --- |
| 普通员工 employee | 问答、点赞、点踩、文字反馈 |
| 运维人员 operator | 创建/编辑文档版本、提交审核、下载 Markdown、登记 Dify 同步/索引、执行并登记 RAG 验证 |
| 管理员 admin | 审核/驳回、最终发布、用户角色管理、全部反馈和审计日志 |

关键规则：

- 运维人员**不能审核**任何文档；
- 运维人员**不能发布**；
- 提交人**不能审核自己提交的版本**，管理员也一样；
- 关联 Dify 的版本，必须由管理员在三项验证都成功后发布。

## 3. 状态模型

### 审核状态

```text
draft（草稿） → pending（待审核） → approved（审核通过）
                       ↘ rejected（已驳回） → 修改后重新提交
```

### 发布状态

```text
unpublished（未发布） → published（已发布）
                              ↓ 新版本发布
                         archived（已归档）
```

### Dify 同步 / 索引 / RAG

| 字段 | 状态 | 含义 |
| --- | --- | --- |
| 同步 | `pending` | 等待人工完成知识库更新 |
| 同步 | `synced` | 已登记 Dify 更新 |
| 同步 | `not_required` | 文档未关联 Dify |
| 索引 | `pending` | 等待确认索引结果 |
| 索引 | `success` | 索引成功 |
| 索引 | `failed` | 索引失败 |
| 索引 | `not_required` | 文档未关联 Dify |
| RAG | `pending` | 等待验证 |
| RAG | `passed` | 验证通过 |
| RAG | `failed` | 验证失败 |
| RAG | `not_required` | 文档未关联 Dify |

## 4. 标准操作流程

```text
┌──────────────────────────┐
│ 1. 运维新增/编辑版本       │  更新原因 + 更新人 + 内容
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 2. 运维提交审核            │  draft/rejected → pending
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 3. 管理员审核              │  approved / rejected
└──────────┬───────────────┘
           │ approved
           ▼
┌──────────────────────────┐
│ 4. 运维下载/复制 Markdown  │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 5. Dify 替换文档 + 重新索引 │
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 6. 运维登记同步 + 索引结果  │  synced + success/failed
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 7. 运维执行并登记 RAG 验证  │  passed/failed
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 8. 管理员发布版本           │  仅 admin
└──────────┬───────────────┘
           ▼
┌──────────────────────────┐
│ 9. 旧发布版本自动归档       │  archived
└──────────────────────────┘
```

### 步骤 1：新增或编辑版本

进入 `/admin/documents`，打开文档：

- 新建版本：点击「新增版本」；
- 编辑草稿：在草稿/已驳回版本详情中点击「编辑草稿内容」。

必须填写：

- 更新原因，例如「补充 Service 日志检查步骤」；
- 文档内容（Markdown/纯文本）；
- 更新人自动记录为当前登录账号。

新版本默认为草稿，不会立即影响 Dify。

### 步骤 2：提交审核

在版本详情页点击「提交审核」，状态变为「待审核」。

系统会记录：

- 提交人账号；
- 提交人用户 ID；
- 提交时间。

### 步骤 3：管理员审核

审核人可以：

- **通过**：状态变为「审核通过」；
- **驳回**：必须填写审核意见，状态变为「已驳回」。运维人员可编辑草稿后重新提交。

**提交人不能审核自己提交的版本**，即使他是管理员。请由另一位管理员审核。

### 步骤 4：下载或复制内容

审核通过后，在版本内容区点击「下载 .md」或「复制内容」。

建议保留文件或文本作为本次 Dify 更新的操作依据。

### 步骤 5：在 Dify 更新知识库

在 Dify 控制台完成：

1. 打开对应知识库；
2. 按文档 ID 找到关联文档（与后台填写的 `dify_document_id` 一致）；
3. 替换文档内容；
4. 保存并等待重新分段、索引完成；
5. 确认索引状态为成功，而不是解析中或失败。

> 如果索引失败，**不要**在本地登记为成功，也不要发布。先修复 Dify 索引问题，或回退 Dify 文档。

### 步骤 6：登记 Dify 同步与索引

回到本地版本详情页，在「Dify 与 RAG 验证」卡片填写：

- 同步说明，例如：
  ```text
  2026-11-06 18:30 在 Dify 替换文档，索引状态 completed；操作人：operator1
  ```
- 索引结果：成功 / 失败。

点击「登记同步与索引」。系统记录：

- 同步状态 `synced`；
- 索引状态 `success` / `failed`；
- 同步说明、登记人、时间。

索引失败时可以修复 Dify 后重新登记。

### 步骤 7：执行并登记 RAG 验证

索引成功后，在版本详情页：

1. 点击「打开聊天页测试」；
2. 使用与本次更新内容相关的真实业务问题；
3. 确认回答来自更新后的知识库；
4. 回到版本页登记：
   - 验证问题；
   - 验证结果（通过/失败）；
   - 验证说明；
5. 提交。

RAG 验证失败时可以修正知识库/问题后重新验证；只有 `passed` 才允许发布。

### 步骤 8：管理员发布

管理员点击「发布此版本」。系统会：

- 校验审核状态为 `approved`；
- 校验 Dify 同步为 `synced`；
- 校验索引为 `success`；
- 校验 RAG 为 `passed`；
- 将当前版本设为 `published`；
- 把之前的发布版本设为 `archived`；
- 写入操作审计。

### 步骤 9：验证与回滚

发布后，再使用真实业务问题验证：

- 新内容能否被检索；
- 回答是否引用了正确文档；
- 旧内容是否仍被错误引用；
- 多轮追问是否正常。

## 5. 字段映射

| 本地字段 | Dify 对应 |
| --- | --- |
| `documents.dify_dataset_id` | 知识库 ID，Dify URL 中 `/datasets/` 后的 ID |
| `documents.dify_document_id` | 知识库中的文档 ID |
| `document_versions.content` | 更新到 Dify 的文本内容 |
| `document_versions.update_reason` | 本地审计字段，不自动写入 Dify |
| `document_versions.updated_by` | 本地更新人 |
| `document_versions.submitted_by` | 本地提交审核的人 |
| `document_versions.dify_sync_note` | 本次 Dify 操作说明 |
| `document_versions.dify_index_status` | Dify 索引结果 |
| `document_versions.rag_status` | 本地 RAG 验证结果 |
| `document_versions.publish_status` | 本地发布状态，不自动改变 Dify 应用 |

## 6. 失败与回滚

### Dify 更新/索引失败

- 本地版本保持「审核通过」和「待同步」或「索引失败」；
- 不登记 RAG 通过，不点击发布；
- 修复 Dify 文档或索引问题后重新登记；
- 如果是错误内容，新建一个版本修正，不要修改已归档版本。

### 已发布版本内容错误

1. 找到上一个已归档版本；
2. 下载旧版本内容；
3. 新建版本，更新原因写「回滚到 vX」；
4. 重新审核、同步 Dify、索引、RAG 验证、发布；
5. 旧错误版本自动归档。

> 归档版本不可重新发布，确保历史链路清晰。

## 7. 与 Dify 官方 API 的关系

Dify 官方提供“用文本更新文档”接口：

```text
POST /datasets/{dataset_id}/documents/{document_id}/update-by-text
Authorization: Bearer {KNOWLEDGE_API_KEY}
```

请求体至少包含 `name` 和 `text`，更新文本后会触发重新索引；知识库接口需要用**知识库 API Key**，不是聊天应用的 App API Key。

官方文档：[Update Document by Text](https://docs.dify.ai/en/api-reference/documents/update-document-by-text)

V1.4 暂不自动调用该接口，原因：

- 需要单独配置知识库 API Key，权限比聊天 Key 更大；
- 索引是异步过程，需要轮询状态；
- 误覆盖生产知识库的代价高；
- 先通过人工确认建立流程和审计，再逐步自动化更稳妥。

未来可扩展为：

1. 管理员配置 `DIFY_KB_API_KEY`（仅后端）；
2. 发布前点击「同步到 Dify」；
3. 后端调用 `update-by-text`；
4. 轮询索引状态；
5. 成功后自动记录 `synced`；
6. 失败时保留待同步，不发布本地版本。

## 8. 操作检查清单

- [ ] 版本有明确的更新原因和更新人
- [ ] 提交人是运维人员/管理员，并已记录
- [ ] 审核通过，且审核人不是提交人
- [ ] 已下载或复制正确版本内容
- [ ] Dify 中对应文档 ID 正确
- [ ] Dify 索引成功
- [ ] 已登记同步说明和索引结果
- [ ] RAG 验证通过，验证问题和结果已登记
- [ ] 管理员完成发布
- [ ] 旧版本已归档
- [ ] 聊天页面已验证新内容可检索
- [ ] 出现异常时有回滚版本方案
